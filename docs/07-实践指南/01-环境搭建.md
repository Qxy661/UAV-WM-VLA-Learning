- **GPU**：NVIDIA RTX 4090 (24 GB) 或 RTX 3090 (24 GB)

## 2. NVIDIA 驱动与 CUDA 安装

### 2.1 确认 GPU 型号与当前驱动

```bash
# 在 Windows PowerShell 中查看 GPU 信息
nvidia-smi

# 输出示例：
# NVIDIA-SMI 546.xx   Driver Version: 546.xx   CUDA Version: 12.x
# GPU Name        | Bus-Id
# NVIDIA GeForce RTX 4090 | 00000000:01:00.0
```

### 2.2 安装/更新 NVIDIA 驱动

访问 [NVIDIA 官方驱动下载页面](https://www.nvidia.com/Download/index.aspx)，选择对应 GPU 型号下载最新 Game Ready Driver 或 Studio Driver。

### 2.3 CUDA Toolkit 安装

当前 PyTorch 主流版本支持 CUDA 11.8 和 CUDA 12.1。建议安装 CUDA 12.1。

**Windows 安装步骤：**

1. 访问 [CUDA Toolkit Archive](https://developer.nvidia.com/cuda-toolkit-archive)
2. 下载 CUDA Toolkit 12.1
3. 运行安装程序，选择"自定义安装"，勾选 CUDA Runtime、CUDA Developer Tools
4. 安装完成后验证：

```bash
nvcc --version
# 应显示：Cuda compilation tools, release 12.1
```

**WSL2 中的 CUDA：**

WSL2 中无需单独安装 CUDA Toolkit，Windows 端的驱动会通过 `/usr/lib/wsl/lib/` 自动映射到 WSL2 内部。只需确保 Windows 端驱动已正确安装。

```bash
# 在 WSL2 终端中验证
nvidia-smi
# 应能看到 GPU 信息
```

### 2.4 cuDNN 安装（可选，但推荐）

cuDNN 通常已包含在 PyTorch 的预编译包中，无需单独安装。如果需要从源码编译 PyTorch 或使用 TensorFlow，请从 [NVIDIA cuDNN](https://developer.nvidia.com/cudnn) 下载安装。

## 8. 常见问题与解决方案

### Q1: `torch.cuda.is_available()` 返回 `False`

- 检查 NVIDIA 驱动是否安装正确：运行 `nvidia-smi`

## 动手验证：硬件需求表里的显存是怎么算出来的？

第 1 节那张表给了每一行的"最低"和"推荐"两栏，但没写这些数是怎么来的。同一份仓库里，7B 微调的显存需求在 07/02 写 18 GB、在 07/06 写 18 和 24 GB、在这张表里是 24/48 GB —— 四个数没有一个和另外三个对得上。

它们不是谁抄错了。显存是四笔账的和：**权重 / 梯度 / 优化器状态 / 激活**。前三笔是精确算术，只要写清楚哪几项算了、按什么精度算，答案唯一；只有第四笔要实测。而四笔里最容易被漏掉的自变量是**每个样本多少个 token** —— 九处表没有一处写它。

### 前三笔的公式，和一列反解表假设的算式

```python
GB = 2 ** 30                                   # 与 nvidia-smi 的口径一致
P7, N_LAYER, D_MODEL = 7.0e9, 32, 4096         # LLaMA-2 7B 的规模
def pad(s, w, right=False):                    # 中文占两格，str.ljust 数不出来
    n = " " * max(0, w - sum(2 if ord(c) > 0x2E80 else 1 for c in s))
    return n + s if right else s + n
def lora(r):                                   # 每层 4 个 d x d 投影，各挂一对 d x r
    return N_LAYER * 4 * 2 * D_MODEL * r
def static_gb(n_frozen, n_trainable):
    """冻结的只存 fp16 一份；可训练的存 fp16 权重 + fp16 梯度 + fp32 两份动量。"""
    return (2 * n_frozen + 12 * n_trainable) / GB
print("一、静态三项是精确算术，算不出花来")
print("  " + pad("配置", 18) + pad("权重", 8, True) + pad("梯度", 8, True)
      + pad("Adam", 8, True) + pad("合计", 8, True))
for name, nf, nt in (("全量 fp16 + Adam", 0.0, P7), ("只推理, fp16", P7, 0.0),
                     ("LoRA r=64", P7, lora(64))):
    w, g, a = 2 * (nf + nt) / GB, 2 * nt / GB, 8 * nt / GB
    print(f"  {pad(name, 18)}{w:>7.1f}G{g:>7.1f}G{a:>7.1f}G{w + g + a:>7.1f}G")
def solve(b1, g1, b2, g2):                     # 设 g = 固定项 + batch x 每样本项
    per = (g2 - g1) / (b2 - b1)
    return g1 - per * b1, per
print("\n二、同一张表里两行只差 batch，就能解出固定项与每样本项")
for name, b1, g1, b2, g2 in (("07/03 ResNet-50", 16, 8.0, 32, 14.0),
                             ("07/04 hidden=256", 32, 10.0, 64, 18.0),
                             ("07/07 DreamerV3", 50, 6.0, 100, 10.0)):
    f, p = solve(b1, g1, b2, g2)
    print(f"  {pad(name, 18)}固定项 {f:>5.2f}G   每样本 {p:>6.3f}G")
```

### 本地实测结果

静态三项（7B 参数）：

```text
  配置                          权重    梯度    Adam    合计 字节/参数
  全量 fp16 + Adam             13.0G   13.0G   52.2G   78.2G        12
  全量 fp32 + Adam             26.1G   26.1G   52.2G  104.3G        16
  只推理, fp16                 13.0G    0.0G    0.0G   13.0G         2
  LoRA r=16 (29M 可训练)       13.1G    0.1G    0.2G   13.4G         2
  LoRA r=64 (117M 可训练)      13.3G    0.2G    0.9G   14.4G         2
```

优化器状态这一项不是推的，是真建一个模型、真走一步 Adam 之后数出来的：

```text
二、优化器状态不是估的：真建一个 66K 参数的模型，真走一步 Adam
  实测 528408 字节 / 66049 参数 = 8.0 字节每可训练参数（一阶动量 fp32 + 二阶动量 fp32，正好 8）
  换算：7B 全量微调这一项要 52.2 GB；
        换成 LoRA r=16，可训练参数只剩 0.42%，这一项塌到 0.22 GB。
```

第四笔账要实测。激活用 `torch.autograd.graph.saved_tensors_hooks` 拦下反向图保留的每个张量：

```text
三、激活：ResNet-50（25.6M 参数，torchvision 原版结构）
  batch    权重+梯度+Adam     激活     合计
  16                0.29G    1.94G    2.23G
  32                0.29G    3.89G    4.17G
  两行相减解出：固定项 +0.00 GB，每样本 0.121 GB。
  固定项是 0 而不是参数那 0.10 GB——因为参数已经在上一段被剔掉了，
  激活里本来就不该有它。两笔账各归各的，才不会重复计入。
```

同一套测量放到 7B 那个宽度上（隐藏 4096、512 个 token）：

```text
四、激活随规模怎么涨（隐藏 4096、512 个 token）
  层数    batch       激活   每层每样本
  1           1    136.1MB      136.1MB
  1           2    272.1MB      136.1MB
  1           4    544.3MB      136.1MB
  2           1    272.1MB      136.1MB
  2           2    544.3MB      136.1MB
  2           4   1088.6MB      136.1MB
  4           1    544.3MB      136.1MB
  4           2   1088.6MB      136.1MB
  4           4   2177.1MB      136.1MB
  归一化之后九格里只差 0.0%——层数和 batch 都是一次方，所以能安全外推。
```

于是得到一把尺子：**8.5 MB/token**（32 层合计），与 batch 无关。拿它去量第 1 节那张表：

```text
六、对账：把文档的数减去静态账，余额能反解出一个没写出来的自变量
  出处            配置                   文档   静态   余额 反解 token
  07/06 GeoChat   LoRA r=64, bs=2         18G  14.4G   3.6G        220
  07/06 GeoChat   LoRA r=128, bs=4        24G  15.7G   8.3G        251
  07/06 GeoChat   全量微调, 4 卡          80G  78.2G   1.8G        213
  07/02 UAV-Flow  LoRA, bs=4, fp16        18G  13.4G   4.6G        139
  07/02 UAV-Flow  LoRA, bs=8, bf16        40G  13.4G  26.6G        401

  统一按 256 token 重算，GeoChat 那三行几乎重合，UAV-Flow 两行还差一截：
  配置                           文档   按 256 token 重算       差
  LoRA r=64, bs=2                 18G               18.6G      +3%
  LoRA r=128, bs=4                24G               24.2G      +1%
  全量微调, 4 卡                  80G               80.4G      +0%
  LoRA, bs=4, fp16                18G               21.9G     +22%
  LoRA, bs=8, bf16                40G               30.4G     -24%
```

三件事从上面这几段里读出来。

**第一，GeoChat 那行"全量微调, 4 GPU → 80 GB/卡"是对的，而且 4 卡并没有让每卡省下显存。** 静态账算出来是 78.2 GB —— 几乎就是它。原因很简单：数据并行复制整个模型，切开的只是 batch。想让每卡少装东西得靠 ZeRO 那类分片，而那张表没写用了什么并行策略。

**第二，LoRA 真正省下的不是权重，是优化器状态。** 权重从 13.0 GB 只涨到 14.4 GB，而 Adam 那一项从 52.2 GB 塌到 0.9 GB。所以第 1 节那张表里"VLM 推理 16 GB / 微调 24 GB"的差距，主要不在参数量，在要不要存两份动量。

**第三，反解出来的序列长度落在 139 ~ 401 token，跨度 2.9 倍。** 这个区间正是 VLM 读一张图加一句指令的量级 —— 没有一行是荒谬的，差的近 3 倍就藏在没人写的那个自变量里。补上它，九张表里的数就能互相换算。

但这把尺子量小模型就不灵了。07/03 那张 ResNet-50 的表自己解出来是固定项 2.0 GB、每样本 0.375 GB，而实测是固定项 **0.00** GB、每样本 0.121 GB —— 每样本差 3.1 倍，还凭空多出 2.0 GB。原因在实测那一段：ResNet-50 的参数一共才 0.29 GB，nvidia-smi 读到的东西里框架开销和显存碎片占了大头，那不是能按算法量算出来的。**7B 那几张表能和实测对上，这张对不上，两码事。看表之前先看模型有多大。**

顺带一个可迁移的算式：**同一张表里只要有两行只差 batch，就能解出"固定项"和"每样本项"两个未知数**，不需要任何额外信息。07/03、07/04、07/07 三张表各自解出来的固定项都是 **2.00 GB** —— 三个不同项目给出同一个整数，更可能是同一种估算习惯，而不是三次独立的测量。

> **限制**：激活那一项是 PyTorch eager 模式量出来的，而且 PyTorch 2.x 的 `nn.MultiheadAttention` 在 `need_weights=False` 时走 SDPA 融合核，**不会**把注意力矩阵留在图里 —— 所以这份账里不含 seq² 那一项，这是现代实现的正常样子。真机上 nvidia-smi 还会多出框架开销、cuDNN workspace 和显存碎片，本节没有算，也不该算进算法需求里。
> 
> 本节只算单卡。ZeRO、张量并行这类分片方案会把静态三项按卡数切开，07/02 和 07/06 里那些"4 卡"的行要按各自实际用的策略另算。
> 
> 反解出的"序列长度"依赖一个前提：那几行之间除了 batch 和 token 数没有别的变量。UAV-Flow 那两行换过精度（fp16 → bf16）和硬件（4090 → A100），所以它们重算后仍差 21% 和 24%，不能全记在序列长度头上。

## 思考题

1. **选型判断**：上面那张硬件需求表里，每一行都有"最低"和"推荐"两栏。如果手上只有一张 RTX 4090（24 GB），表里哪些项目跑得动、哪些跑不动？判断时说清楚你用的是哪一栏。

2. **环境隔离**：Q4 反复强调 ROS2 环境和深度学习环境不要混用。为什么混用会出问题？文档给出的具体操作规则是什么？

3. **排障顺序**：`torch.cuda.is_available()` 返回 `False` 时，Q1 列了四条可能原因。在 **WSL2** 这个特定环境下，你会按什么顺序排查？为什么某一条在 WSL2 里其实很少是真正的原因？

4. **成本权衡**：Q7 给了五种应对显存不足的方法。对一个 7B VLM 的 LoRA 微调任务、在 24 GB 卡上，你会优先选哪一种？为什么不是另外几种？

5. **验证的边界**：第 7 节那个环境验证脚本靠逐个 `import` 来检查。它检查不到哪些东西？"全部 [OK]" 能说明什么、不能说明什么？

<details><summary>参考答案</summary>

1. 关键是把两栏分开看。**推荐栏**里只有 VLM 推理（7B，24 GB）正好对上 4090；**最低栏**里能跑的是 VLA 模型（24 GB）、扩散模型训练（24 GB）、扩散推理（12 GB）、世界模型训练 DreamerV3（12 GB），以及不需要 GPU 的 PX4 SITL 和数据集处理。而 VLM 微调（推荐 48 GB）、扩散模型训练（推荐 80 GB A100）用 4090 会吃紧或跑不动 —— 注意扩散训练那一行"最低 24 GB"和"推荐 80 GB"差距极大，说明这一行的最低配置实际体验会很勉强。文档给的替代方案是云 GPU（Colab Pro / AutoDL / Lambda Cloud）。

2. ROS2 Humble 默认绑定系统 Python 3.10，而 conda 环境会改写解释器和 `PYTHONPATH`。混用后 `import rclpy` 要么直接失败，要么加载到用错误 Python 版本编译的扩展模块。文档给的规则很明确：**ROS2 终端只 `source /opt/ros/humble/setup.bash`，不要 `conda activate`；深度学习终端只 `conda activate uavvla`，不要 source ROS2 的 setup.bash。** 也就是用两个终端把两套环境物理隔开。

3. 先跑 `nvidia-smi` —— 成本最低，且能一票否决。WSL2 的特殊性在于：**不需要在 WSL2 里单独装 CUDA Toolkit**，Windows 端驱动会通过 `/usr/lib/wsl/lib/` 自动映射进来。所以"WSL2 里没装 cuda-toolkit"这条通常不是真因，该查的是 **Windows 端的驱动版本是否够新**。之后才轮到 PyTorch 版本与 CUDA 是否匹配，最后查 `CUDA_VISIBLE_DEVICES`。

4. 优先 **4-bit 量化（bitsandbytes）+ gradient checkpointing**。理由：LoRA 本身已把可训练参数压得很低，配 4-bit 量化加载基座是这个组合的标准做法，而 6.3 节已经把 `peft` 和 `bitsandbytes` 装好了。半精度（方法 1）对本来就用 fp16 训练的任务收益有限；DeepSpeed ZeRO（方法 3）主要面向多卡或分片优化，单卡收益不如前两者直接；减小 batch_size（方法 4）直接拉长训练时间，通常留作最后手段。

5. 它只覆盖 **Python 侧**。检查不到：CUDA 版本与 PyTorch 是否真正兼容（`is_available()` 为 `True` 时算子仍可能不匹配）、ROS2 / PX4 / MAVROS 这些非 Python 组件、MAVROS 需要的 GeographicLib 数据集是否安装，以及 `xformers` 这类只在运行时才报错的算子包。所以"全部 [OK]"是**必要不充分**条件 —— 它排除了一批低级问题，但不能保证后面复现时不出环境问题。
