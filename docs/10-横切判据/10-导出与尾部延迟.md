## 四个约束

| 约束 | 具体要求 | 常见失败 |
|---|---|---|
| shape 固定 | batch、分辨率、历史帧数在导出时写死 | 动态维度让推理引擎无法选核，或退化成最慢 profile |
| 算子支持 | 图里每个算子有目标端实现 | 自定义算子、某些归一化与注意力变体不支持 |
| 数值范围 | 量化后精度损失可接受 | INT8 对 LayerNorm 与 softmax 敏感 |
| 延迟尾部 | 报告 P99 与最大值 | 只报均值，长尾被平均掉 |

## 固定 shape 的代价

动态 shape 看着灵活，实际代价是引擎必须为区间内每个尺寸准备 kernel，或退化到最保守的实现。工程做法是导出两到三个固定档（例如 160² 与 224²），按需切换。

导出时容易被忽略的一条：任何依赖数据的控制流（例如按 token 数分支的注意力）在 trace 时会被固化成当时那条路径。导出后换个输入长度，结果就错，且不会报错。

本库 `code/n_quant_bits.py` 量的是量化对表征的影响：同一位宽下，压掉的不是均匀的信息，先在细粒度空间量上崩。这与 `code/w_token_budget.py` 的结论同构——压预算时先崩的是定位类信息，不是语义类。

## 尾部延迟为什么决定安全

控制回路的稳定性取决于最坏响应时间。均值 20 ms、P99 200 ms 的系统，看起来"实时"，但每 100 次就有一次晚到 180 ms。在 250 Hz 内环上，这等于有 45 个周期在执行过期指令。

`code/f_control_loop.py` 把这件事量化了：外环延迟 1 秒时，闭环横向滞后达到十几厘米（实测 16 cm）。延迟从 20 ms 涨到 200 ms 时，滞后按比例放大，而速度越快放大越明显。

报告口径建议固定为四列：P50、P90、P99、max，并注明测量时长与输入分布。只报 P50 等于只报了最好的一半。

## 量化与校验

INT8 后训练量化（PTQ）的最小流程：

1. 用真实输入分布采 200–500 个校准样本（不是随机噪声）。
2. 逐层量化，先只量化卷积与矩阵乘，LayerNorm 与 softmax 保留 FP16。
3. 在 hold-out 上比 FP16 与 INT8 的输出差异：策略输出用动作 L2 与成功率，感知用 mAP 或位置误差。
4. 差异超过任务容差时回退到 FP16，或改量化感知训练（QAT）。

第 3 步常被跳过。跳过后的典型现象是"离线精度只掉 0.3 个点"，但闭环成功率掉一半——因为误差集中在决策边界附近，离线指标对它不敏感。

## 判据表

| 检查项 | 通过条件 | 不通过时 |
|---|---|---|
| shape | 导出与推理用同一组固定尺寸 | 动态维度必须给出 profile 上下界 |
| 算子 | 导出后逐个算子核对目标端支持表 | 有自定义算子则需插件，工期要算进去 |
| 数值 | 报 FP16 与量化后的差异，含闭环指标 | 只报离线精度时结论降级 |
| 延迟 | P50／P90／P99／max 四列齐全 | 只有均值时不可用于安全论证 |
| 输入分布 | 说明延迟测量时的输入来自真实场景 | 用随机张量测的延迟只是下界 |
| 回退 | 有 INT8 失败时切 FP16 的开关 | 无回退则量化失败等于上线失败 |

## 边界

仿真与桌面 GPU 上的延迟不能外推到板上：同样的模型，桌面 8 GB 显卡与机载 8 GB 模块的吞吐可以差 5 倍以上，原因在带宽与散热，不在算力标称值。唯一可信的测量是目标板、固定 shape、真实输入、跑够 1000 次。

对于 8 GB 显存的本地环境，模型规模上限大约在十亿参数以内（FP16 权重占 2 GB，激活与 KV 另算）。这条上限决定了很多方案在选型阶段就该被排除，而不是等到部署时才发现装不下。
