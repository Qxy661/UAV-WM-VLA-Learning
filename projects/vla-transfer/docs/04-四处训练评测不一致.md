# 04 四处"训练和评测不一样"

同一类错误在这个项目里犯了四次，每一次都给出了一个方向正确的错结论。写成一页，
是因为它们值得被当成一条工程规则，而不是四个偶然的 bug。

| # | 不一致 | 表现 | 造成的错结论 |
|---|---|---|---|
| 1 | 评测漏 `--residual` | 四格全 0/60 | "新判据把策略弄坏了" |
| 2 | 验证集漏 `residual=` | `val_mse` 恒在目标方差附近 | "盲训练与能看见的一样好 → 视觉没进决策" |
| 3 | `substeps` 默认 5 | 所有闭环慢 5 倍 | "策略飞不到位是感知问题"（实际是执行速度） |
| 4 | `last_label` 只在策略调用时更新 | DAgger 集图文错位 | "DAgger 帮了倒忙"（实际是标签陈旧） |

## 1 评测漏 `--residual`

训练 `--residual`、评测不带 → `ChunkPolicy` 把残差当绝对动作解释，推力被当成
0–21 N 的绝对值，每拍往地面或天上怼。四格同时 0/60，看起来像"判据太严"。

## 2 验证集漏 `residual=`

```python
tr = ChunkDataset(root, ("train",), ..., residual=a.residual, ...)
va = ChunkDataset(root, ("val",),   ..., horizon=a.horizon)   # 少了 residual
```

验证目标是绝对动作、模型输出是残差，MSE 就落在目标方差上（实测 21.9978）。
历次 `val_mse 21.3 / 25.5 / 25.86` 全是这个数附近的抖动，**不衡量拟合**。
修好之后的真实单步误差是 0.21（相对方差 1%）。

这一条最危险，因为它不报错、数字稳定、方向符合直觉（"盲训练不掉点，所以视觉无用"）。

## 3 `substeps()` 返回 5

`CONTROL_HZ / ACTION_HZ = 48 / 9.6 = 5`，看起来是把 9.6 Hz 的动作铺到 48 Hz 的控制上，
但训练目标是**逐控制步**的动作（`obs.npz` 的 `action` 是 48 Hz 逐步记录的），
所以每个动作只能执行 1 个控制步。默认 5 等于把整段速度放慢 5 倍。

实测 hold=5 与 hold=1 的 60 集成功率逐位相同（0.217 / 0.000 / 0.183），
所以它不是本轮结论的原因，但它是**所有闭环评测慢 5 倍**的原因，早该修。

## 4 `last_label` 陈旧

`_label()` 原来只读 `policy.last_label`，而它仅在策略被调用那一拍更新
（`--policy-every` 默认 4）。于是每 4 拍有 3 拍记的是三拍之前的专家动作。
专家集不走这条路（`policy is None` 时现算），所以**只有 DAgger 集被污染**——
这正好解释了"看得见的模型被打到 0、盲模型不受影响"。

修法：`DaggerPolicy.label(st, ref, yaw_ref)` 在记录时现问一次专家。

## 一条可以带走的规则

这四个 bug 都是"同一个开关必须在训练与评测两侧一致"，而四次都是靠人眼核对的。
正确做法是让代码拦：`ckpt.pt` 里已经存了 `args`，评测脚本启动时应当比对

- `args.residual` ↔ `--residual`
- `args.horizon` ↔ 预测块长
- `args.blind` ↔ `--blind`
- `args.action_space` ↔ `--action-space`

不一致直接退出，而不是跑完 60 集再让人去猜。这条已列进 `STATUS.md` 的队列，
尚未实现——在实现之前，**任何一次"结果突然变成 0"都先查参数**。
