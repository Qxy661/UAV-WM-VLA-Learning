# 01 为什么在 24 个 demo 之外还要一个系统

## 先说清两件事的区别

`code/` 下的 24 个 demo 是**认知验证**：一个脚本回答一个具体问题，单文件、合成数据、
几十秒跑完。它们的问题是设计好的，结论写在同一份终端输出里。这类代码的价值在于
"把一句话变成一个可检验的量"，比如 `code/t_wm_diagnostics.py` 用 √30 ≈ 5.477 验证
"单步误差放大到 30 步"这件事到底是不是 5.477 倍。

`projects/uav-inspect/` 是**工程验证**：它回答的是另一类问题：当这些结论要拼成一个
能连续跑、能被别人接手、失败会自己暴露的系统时，还剩下哪些坑。

两条判据可以立刻把两者分开：

| | demo | 系统 |
|---|---|---|
| 谁来用 | 作者自己看结论 | 别人改一个参数再跑 |
| 数据从哪来 | 脚本里生成 | 录制、划分、统计、版本 |
| 错了会怎样 | 数字不对，重跑 | 不报错但指标静默失效（更麻烦） |
| 数字可信吗 | 单次运行 | 固定协议 + 区间 + 拒绝比较 |

## 这一层要证明的四件事

1. **频率是真的分层的**。物理 240 Hz、控制 48 Hz、相机 10 Hz、策略 5 Hz（M4 起）。
   写在同一句注释里不算，要能在 `metrics.json` 里看到每一层的 P50/P99 和周期抖动。
2. **指标口径写在代码里，不写在文档里**。覆盖率的分母是"几何上看得见的视点"，
   最小间距的判定带碰撞半径，成功率要求"到了并停住"。这些定义如果只写在 README，
   下一个人换个写法就能得出相反结论。
3. **失败模式可见**。安全层不是 try/except，是独立一票否决 + 降级阶梯；数据集的可见性
   标签错了要能被基线打回（这正是 M3 里真实发生过的：红色像素阈值量纲写错，标签全 0，
   可见性 AUC 恒 0.500，不报错）。
4. **别人能接**。配置文件有范围校验、坏配置加载即报错；每个里程碑有命令、产物、
   判定条件；CI 跑最小子集。

## 已完成到哪一步

| 里程碑 | 验收 | 结果 |
|---|---|---|
| M0 单机悬停 | RMSE ≤ 0.20 m | 0.0117 m，最大倾角 0.00° |
| M1 四机交叉 | 间距 ≥ 0.6 m | 1.165 m（未调参 0.28 m） |
| M2 巡检录制 | 覆盖率可判定 | 8 集 958 帧，可行视点 100% |
| M3 世界模型 | 开环误差 < persistence | 0.290 对 0.334（开发机待复跑） |
| M5 安全层 | 四类故障零碰撞 | 四类通过，最高挡 HOVER |
| M6 评测口径 | 三基线同口径对比 | scripted 100%，另两个 0% |
| M4 / M7 | 指令跟随 / ONNX 导出 | 未完成 |

## 明确不做的事

- 不做真实飞行控制栈（PX4 / ROS2 那条链）。本机装不上，也不是这个仓库要证明的东西。
- 不做多机通信仿真（丢包、时钟偏移）。M1 只验几何冲突，不验分布式一致性。
- 不做照片级渲染。解析式相机的取舍写在 ADR-010，它的用途是给世界模型提供"有结构、
  可复现、算得快"的输入，不是替代渲染器。
