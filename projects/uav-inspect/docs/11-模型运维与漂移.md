# 11 模型运维：run 注册表与输入漂移

系统跑到后面会出现一种很隐蔽的错误：**把两次不同口径的跑分放进同一张表**。数据换过、
配置改过、commit 不同，但 `metrics.json` 里只有数字。registry 把「模型-数据-配置-分数」
绑成一条记录，report 只读注册表，不猜。

## 注册表里有什么

一条 JSONL 记录：

```json
{"run_id": "m1_multi-20261028T1122", "kind": "m1", "git": "8521b55",
 "data_hash": "sha256:9d1c…", "config": {"d_safe": 0.6}, "metrics": {"passed": true}}
```

`data_hash` 用**文件名 + 大小**哈希，不读内容：几十 GB 的数据集读一遍要几分钟，而
「同名文件大小变了」已经足够发现换数据。要防篡改就换成内容哈希，代价是慢。

实测（本机 8 个 run）：

| run | kind | 分数 |
|---|---|---|
| m0_hover | m0 | passed=True |
| m1_multi | m1 | passed=True |
| m3_wm | m3 | passed=True |
| m5_faults | m5 | passed=True |
| m2_dataset / m6_eval / m7_deploy / e4_compare | — | 无 success_rate（不是判据型产物） |

`--best success_rate` 只在有该字段的记录里挑，挑不到会说"没有可比记录"，而不是拿
`passed` 去冒充。

## 漂移用 PSI，不用 KL

PSI 有通用阈值：< 0.1 稳定、0.1–0.25 关注、> 0.25 报警。KL 一旦某个箱子里出现 0 就
发散，得手动加 eps，反而不如 PSI 好解释。

实测（同一份数据 vs 同一份数据、以及把图像亮度整体 ×1.2）：

| 场景 | PSI | 判定 | 参考均值 → 当前均值 |
|---|---|---|---|
| 同分布 | 0.000 | stable | 0.3869 → 0.3869 |
| 亮度 +20% | **5.106** | alert | 0.3869 → 0.4578 |

阈值不是拍的：`psi()` 按参考分布的分位切 10 箱，比例变化直接进公式，所以「整体亮了
20%」会给出远超 0.25 的值，而「同样的分布重采样」给出 0。

## 这条线为什么值得做

换仓库布局、换相机曝光、换目标颜色，都会先在**输入分布**上反映出来。等闭环指标掉了
再反应就晚了——那时已经在用旧模型飞新场景。E9 的作用是把这件事提前到「还没起飞」。

## 不能证明什么

- 亮度只是一个代表量。目标从红色换成蓝色，亮度几乎不变，PSI 不会响——这种漂移要靠
  颜色直方图或直接用闭环指标发现。
- 注册表不存权重文件，只存路径与哈希；权重丢了照样查得回配置，但恢复不了模型。
- PSI 依赖参考集的选择。用测试集当参考，就会把"测试集也在漂"这件事掩盖掉。

## 复现

```bash
py -3.9 projects/uav-inspect/scripts/e9_report.py --register
py -3.9 projects/uav-inspect/scripts/e9_report.py --best success_rate
py -3.9 projects/uav-inspect/scripts/e9_report.py \
  --drift-ref <参考数据根> --drift-cur <待检数据根>
```
